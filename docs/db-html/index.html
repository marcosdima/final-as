Arquitectura del Asistente Virtual Inteligente (RAG) & Motor Vectorial

El módulo isft189 implementa un pipeline completo de Generación Aumentada por Recuperación (RAG) integrado en PostgreSQL 16 con la extensión pgvector. Almacena normativas institucionales, planes de estudio y resoluciones vectorizadas con un modelo denso de 384 dimensiones, indexadas con algoritmo HNSW para búsquedas semánticas sub-milisegundo mediante distancia de coseno.

PostgreSQL 16 + pgvector 0.5+ Embedding: 384 dimensiones Índice: HNSW (vector_cosine_ops) Métrica: Similitud Coseno (<=>) Inmutabilidad y Auditoría
FASE 01
Ingestión & Chunking
Extracción de resoluciones, correlatividades y planes de estudio oficiales. Segmentación en chunks de 512 tokens con 50 tokens de solapamiento para preservar coherencia sintáctica.
isft189.documentos_metadata
FASE 02
Incrustación Vectorial
Generación de representaciones vectoriales densas ∈ ℝ384 mediante modelos del estado del arte (all-MiniLM-L6-v2). Mapeo semántico que captura sinónimos institucionales.
all-MiniLM-L6-v2 (384d)
FASE 03
Indexación HNSW
Construcción del grafo de búsqueda aproximada (HNSW: m=16, ef_construction=64) sobre la columna embedding vector(384) para consultas sub-10ms con operador <=>.
isft189.documentos_vectoriales
FASE 04
Aumento & Inferencia
Recuperación top-k de fragmentos relevantes, inyección de contexto verificado en la ventana de contexto del LLM y registro de la interacción para auditoría y evaluación continua.
isft189.historial_consultas

Consulta Vectorial en Tiempo Real (Operador <=> de Coseno con pgvector) 

SELECT 
    d.titulo AS documento_origen,
    v.contenido AS fragmento_recuperado,
    ROUND((1 - (v.embedding <=> '[0.042, -0.015, ..., 0.089]'::vector))::numeric, 4) AS similitud_coseno
FROM isft189.documentos_vectoriales v
JOIN isft189.documentos_metadata d ON d.id = v.documento_id
WHERE d.activo = true
ORDER BY v.embedding <=> '[0.042, -0.015, ..., 0.089]'::vector
LIMIT 3;

Automatización en el Motor: Log, Trigger y Procedure

Además de las tablas y restricciones, el esquema instituto incorpora una capa de automatización en PL/pgSQL definida en el script db/instituto/03_trigger_procedure_log.sql. Tres piezas trabajan juntas: una tabla de log de eventos, un trigger que audita los cambios de nota final y un procedure que cierra un acta de examen con validaciones y registro automático.

PostgreSQL 16 · PL/pgSQL 1 trigger AFTER UPDATE 1 procedure CALL Log append-only con JSONB
PIEZA 01
Log de eventos
Tabla instituto.log_eventos append-only con nivel (INFO/WARN/ERROR), origen, mensaje, detalle JSONB y usuario de base. La función fn_log() centraliza la escritura: cualquier rutina registra un evento con una sola llamada.
log_eventos · fn_log()
PIEZA 02
Trigger de auditoría
trg_log_nota_final se dispara AFTER UPDATE OF nota_final sobre inscripcion_examen. Compara OLD y NEW con IS DISTINCT FROM y solo escribe si la nota cambió, guardando el valor anterior y el nuevo.
inscripcion_examen · fn_log_nota_final()
PIEZA 03
Procedure de cierre
sp_cerrar_acta(p_acta_id) bloquea el acta con FOR UPDATE, valida su estado, cuenta inscriptos y notas cargadas, la marca CERRADA con fecha de cierre y deja el evento en el log. Si ya estaba cerrada, registra un WARN y no modifica nada.
CALL sp_cerrar_acta(id)

Flujo interno de sp_cerrar_acta

  1. Bloquea la fila: SELECT estado, numero ... FOR UPDATE evita cierres simultáneos.
  2. Valida existencia: si no hay fila, lanza RAISE EXCEPTION.
  3. Cierre idempotente: si el acta ya está CERRADA, escribe un WARN y retorna sin tocarla.
  4. Mide: cuenta inscriptos y cuántos tienen nota_final cargada.
  5. Actualiza: estado = 'CERRADA' y fecha_cierre = now() en un solo UPDATE.
  6. Registra: inserta un evento INFO en log_eventos con las métricas.
  7. Informa: emite un RAISE NOTICE con el resumen del cierre.

El procedure corre dentro de la transacción del llamador: si este hace ROLLBACK, se revierten tanto el cierre como el log. No ejecuta COMMIT por su cuenta.

Definiciones SQL

01 · log_eventos + fn_log() 
CREATE TABLE instituto.log_eventos (
    id          BIGSERIAL    PRIMARY KEY,
    fecha       TIMESTAMPTZ  NOT NULL DEFAULT now(),
    nivel       VARCHAR(10)  NOT NULL DEFAULT 'INFO',  -- INFO | WARN | ERROR
    origen      VARCHAR(60)  NOT NULL,                -- componente que emite el evento
    mensaje     TEXT         NOT NULL,
    detalle     JSONB        NOT NULL DEFAULT '{}'::jsonb,
    usuario_bd  TEXT         NOT NULL DEFAULT current_user,
    CONSTRAINT ck_log_eventos_nivel
        CHECK (nivel IN ('INFO', 'WARN', 'ERROR'))
);

CREATE OR REPLACE FUNCTION instituto.fn_log(
    p_nivel VARCHAR, p_origen VARCHAR, p_mensaje TEXT,
    p_detalle JSONB DEFAULT '{}'::jsonb
) RETURNS BIGINT LANGUAGE plpgsql AS $$
DECLARE v_id BIGINT;
BEGIN
    INSERT INTO instituto.log_eventos (nivel, origen, mensaje, detalle)
    VALUES (p_nivel, p_origen, p_mensaje, COALESCE(p_detalle, '{}'::jsonb))
    RETURNING id INTO v_id;
    RETURN v_id;
END;
$$;
02 · trigger de auditoría de nota final 
CREATE OR REPLACE FUNCTION instituto.fn_log_nota_final()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
    IF NEW.nota_final IS DISTINCT FROM OLD.nota_final THEN
        PERFORM instituto.fn_log(
            'INFO', 'trg_nota_final', 'Nota final modificada',
            jsonb_build_object(
                'inscripcion_examen_id', NEW.id,
                'alumno_id',             NEW.alumno_id,
                'mesa_examen_id',        NEW.mesa_examen_id,
                'nota_anterior',         OLD.nota_final,
                'nota_nueva',            NEW.nota_final
            )
        );
    END IF;
    RETURN NEW;
END;
$$;

CREATE TRIGGER trg_log_nota_final
AFTER UPDATE OF nota_final ON instituto.inscripcion_examen
FOR EACH ROW EXECUTE FUNCTION instituto.fn_log_nota_final();
03 · procedure de cierre de acta 
CREATE OR REPLACE PROCEDURE instituto.sp_cerrar_acta(p_acta_id BIGINT)
LANGUAGE plpgsql AS $$
DECLARE
    v_estado instituto.estado_acta;
    v_numero INT; v_total INT; v_cargadas INT;
BEGIN
    SELECT estado, numero INTO v_estado, v_numero
      FROM instituto.acta_examen
     WHERE id = p_acta_id
       FOR UPDATE;

    IF NOT FOUND THEN
        RAISE EXCEPTION 'El acta % no existe', p_acta_id;
    END IF;

    IF v_estado = 'CERRADA' THEN
        PERFORM instituto.fn_log('WARN', 'sp_cerrar_acta',
            'Intento de cerrar un acta ya cerrada',
            jsonb_build_object('acta_id', p_acta_id, 'numero', v_numero));
        RAISE NOTICE 'El acta % ya estaba cerrada; no se modificó.', p_acta_id;
        RETURN;
    END IF;

    SELECT count(*), count(nota_final) INTO v_total, v_cargadas
      FROM instituto.inscripcion_examen
     WHERE acta_examen_id = p_acta_id;

    UPDATE instituto.acta_examen
       SET estado = 'CERRADA', fecha_cierre = now()
     WHERE id = p_acta_id;

    PERFORM instituto.fn_log('INFO', 'sp_cerrar_acta', 'Acta cerrada',
        jsonb_build_object('acta_id', p_acta_id, 'numero', v_numero,
                           'inscriptos', v_total, 'con_nota', v_cargadas));

    RAISE NOTICE 'Acta % (N° %) cerrada: % inscriptos, % con nota final.',
        p_acta_id, v_numero, v_total, v_cargadas;
END;
$$;

Prueba real ejecutada sobre la base 

BEGIN;
  UPDATE instituto.inscripcion_examen SET nota_final = 9.25 WHERE id = 1;
  CALL instituto.sp_cerrar_acta(4);
  CALL instituto.sp_cerrar_acta(1);   -- ya estaba cerrada
  SELECT * FROM instituto.log_eventos ORDER BY id DESC;
ROLLBACK;

La prueba se ejecutó dentro de BEGIN ... ROLLBACK para no alterar los datos de demostración: los tres eventos se generaron y luego se revirtieron junto con el cierre del acta.

Cómo ejecutarlo 

-- 1) Crear los objetos (después de 01_ddl.sql y 02_dml.sql)
psql -U tpi -d isft189 -v ON_ERROR_STOP=1 -f db/instituto/03_trigger_procedure_log.sql

-- 2) Usar el procedure
CALL instituto.sp_cerrar_acta(4);

-- 3) Modificar una nota: el trigger registra solo
UPDATE instituto.inscripcion_examen SET nota_final = 9.25 WHERE id = 1;

-- 4) Consultar la bitácora
SELECT id, fecha, nivel, origen, mensaje, detalle
  FROM instituto.log_eventos
 ORDER BY id DESC LIMIT 10;

Si se vuelve a ejecutar 01_ddl.sql, el DROP SCHEMA instituto CASCADE elimina estos objetos y hay que reejecutar el script 03. La tabla de log crece de forma indefinida: a futuro conviene una política de retención o particionado mensual.
